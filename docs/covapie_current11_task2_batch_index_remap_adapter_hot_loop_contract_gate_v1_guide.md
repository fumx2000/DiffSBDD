# CovaPIE Current11 Task2 remap adapter hot-loop contract gate V1

This Exact4 is a design and implementation contract gate for a future explicit remap-authority context and output-only fast path. It is not the context/runtime product, a fast runtime product, an adapter refactor, shared-kernel work, DataLoader integration, model/head/loss work, or training.

The current slow public adapter remains byte-for-byte and API/Exact2-semantic unchanged. V1 does not extract a shared kernel. A future fast path must orchestrate the frozen adapter private pure helpers `_validate_source_contract`, `_remap_engine`, `_failure_output`, `_validate_output`, `_provenance`, and `_readiness`; it must not copy the full remap algorithm or define another status precedence.

The future product exposes exactly two keyword-only functions: `build_covapie_current11_task2_batch_index_remap_adapter_context_v1(*, repo_root, state_root)` and `remap_covapie_current11_task2_batch_index_with_context_v1(*, context, adapter_input)`. The context class is not public. Its logical Exact20 payload is opaque, tamper-evident, semantically immutable, deeply immutable in representation, and sealed over all semantic fields. V1 defines no pickle contract.

On a clean tracked successor, one context build consumes the published Output17 reconciliation gate exactly once and the remap predecessor-successor exactly once. The successor retains its own one-build/one-B2 contract; the context builder makes no direct B2 call and does not call the historical remap gate, adapter `_contract_exact6`, or historical payload/instance builders. It parses successor stable5 plus the successor report without calling the old `_parse_contract` or fabricating an old report.

The future context product has a two-stage repository lifecycle. While its Exact4 is precommit-untracked, only fixture/unit/candidate validation may use test-harness-only exact predecessor artifact injection; the real public context build is not required to succeed because published predecessors correctly observe the untracked files. Only a clean committed successor requires live reconciliation-once, successor-once, and real context-build proof. Production monkeypatching, Git-status hiding, and predecessor modification are forbidden.

The gate report's context/runtime-candidate readiness follows the gate's own repository lifecycle. A `precommit-untracked` gate reports `ready_for_remap_adapter_context_runtime_implementation=false` with blocker `hot_loop_contract_gate_not_published`. A `clean-tracked-successor` gate reports that candidate readiness as true with blocker `NONE`. This authorizes only the later context/runtime implementation candidate; it does not claim that the product exists, passes, or makes the public hot-loop runtime ready. The future context Exact4 is not part of this gate increment and may be created only by a later, separately authorized context/runtime increment.

Context freshness is `explicit_rebuild_by_owner`. An owner builds one context per process or DDP rank per authority snapshot and explicitly rebuilds it when needed. There is no global registry, global or LRU cache, hidden singleton, mutable hidden cache, cross-process shared cache, silent refresh, or per-batch filesystem freshness check. A stale context remains bound to its construction authority snapshot and makes no current-filesystem/current-successor claim.

Each future fast call validates context type/version/seal, rejects invalid input types, preserves caller input and context, applies the current adapter's exact schema semantics, and returns one built-in Output17 dict only. It returns no adapter/successor/contract report and no bytes bundle. For the same exact input, its canonical Output17 bytes must match the current public adapter's whole Exact17 on success and deterministic fail-closed failure, including provenance, readiness, offsets, validity, failure placement, nulls, field order, and bool/int types.

The historical private failure producer is not the runtime golden and failure normalization is forbidden. The old adapter report is neither returned nor authoritative for the fast path because its historical live-gate claims do not describe cached successor authority. No new fast report is defined.

Per batch, the fast path performs no reconciliation, successor, B2, historical gate, `_contract_exact6`, old `_parse_contract`, formal validation, filesystem read, Git/subprocess call, report generation, artifact write, global-cache lookup, or context rebuild. This is a structural performance contract. It defines no absolute latency SLA, benchmark-loop requirement, or one-shot millisecond threshold; the reviewed C/D timing is directional evidence only.

The gate itself is lightweight and does not call the current adapter public build, reconciliation/successor/B2 public builds, the historical remap gate, one-heavy C/D, or the lightweight probe again. It validates the frozen published sources and the identities/required conclusions of the three reviewed reports, builds a deterministic in-memory Exact6 twice under the checker, and writes nothing.

The future context/runtime product remains unimplemented in this increment. Publication of this gate enables only its separately authorized implementation candidate. The public hot-loop product remains unimplemented, the current adapter still does not directly accept successor Exact6, the compiler context does not consume successor authority, and compiler-context rebuild device-identity risk remains. DataLoader, model, and loss integration are not ready. Step12D remains a smoke legality check, not a final training-feature contract; the historical unknown-atom/feature-semantics state requires formal re-audit before training, and training is not ready.

Canonical V1 remains exactly five masks: `warhead_only/A`, `linker_plus_warhead/B`, `scaffold_plus_warhead/B2`, `scaffold_only/B3`, and `scaffold_plus_linker_plus_warhead/C`. This gate changes no mask.
